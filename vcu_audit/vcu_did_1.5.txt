Introduction
Scope
This document provides the detailed engineering specification of Telluride Video Codec Unit for a target process technology of 7nm. The detailed specifications are based on the Everest (Telluride) MMD VCU architecture requirements.

VCU supports both video compression and decompression with different rates. It supports the multiple standards including H.264 and H.265. It is a hardened block with 1 instance of multi-dual core encoder and 1 instance of multi-single core decoder.

Block Diagram
The block diagram for the VCU is shown in the Figure 2. VCU replaces 2 GT tiles and full PnR of VCU is planned as there would not be any gap between 2 GTs.  The main features of VCU includes video compression and decompression. This is achieved using 1-1 instance of dual core encoder and single core decoder. The encoder captures the live video in the frame buffers. The encoder cores fetch frame from frame buffers, compresses/encodes and stores back into the memory. The decoder unit fetches the compressed frame along with reference frames from frame buffer, decompresses and stores back in the frame buffer.  The access to the DDR memory is through MMD NoC extension. Access to the memory does not involve any PL based AXI ports.  The encoder has four clock ports – IP clock, AXI clock, APB clock and MCU clock. All the four clocks will be driven from a single DPLL clock source. Similarly, a single DPLL clock source is used to drive all four clocks for Decoder.The clocks for AXI-M ports, VCU core, MCU are received from DPLL in GT Clocking Column.  The clock for AXI-S port is also received from DPLL. NMU takes VCU as master and communicates via AXI 4 -Master interface. NSU takes VCU as slave and communicates via AXI-S interface. PL is powered on and functional before VCU can be functional. For performance monitoring, AXI interfaces are monitored using APM to measure AXI transaction counts, latencylatency, and bandwidth. The VCU block have a dedicated power domain VCUINT_VCU for its core blocks. Along with it, VCU is interacting with three other power domains: VCCINT (PL), VCCINT_SOC (NoC) and VCCRAM (GTCC DPLL).  Encoder cores will be at Level 1 hierarchy and rest of VCU blocks will be at Level 2 hierarchy.

Block Level Description
Encoder Subsystem
VCU comprises one instance of dual core encoder to process at pixel levels. The RISC-V controller interfaced with the encoder handles the higher levels of encoder process, above the slice data level. The IP reads the current frame along with additional reference frames from frame buffers, encodes it and again writes back into the memory via 128-bit AXI-M interface. It includes a cache for reducing DRAM bandwidth by reusing data fetched for motion estimation and other purposes. It uses L1 and L2 caches in form of RAMs and are internal. The caches are not available for external use.

Encoder cores are synthesized separately at L1 level and the rest of IP logic including MCU, interfaces is synthesized at L2 Level. Because of size, Encoder + MCU cannot be fitted in a single physical partition. As per architecture specs, it takes an area of around 4.9 sqmm on SoC and MCU unit takes an area of 0.15 sqmm. It supports 4k x 2k @60fps for both UHD & DCI formats.  It supports H.264 (Advanced Video Coding) and H.265 (High Efficiency Video Coding) standards.

NoC NSU can reset the Encoder IP using the RESET register through APB interface via interconnect. The RESET register provides combination of reset bits to reset specific units/cores.

Encoder IP is disabled by disabling the clock based on SSC output eFuse Disable signals. The e-Fuse bits would be coming from PMC, VCU2 receives the 64-bit packet over SSC channel and decodes it to generate eFuse Disable signals.

 Encoder subsystem comprises:
Two cores: The Encoder IP uses two cores for pixel level processing. It compresses the data as per the requested standards and color formats. It processes the low-level commands which are either stored in hardware registers or a list of such commands stored in the external memory.

RISC-V MCU:  The encoder parameters are controlled by MCU and configured using a register map through an internal peripheral bus. The high-level commands for video encoding are processed by MCU and MCU generates slice/tile level commands to Encoder cores. The 64-bit RISC MCU have:
128-bit AXI-4 Interface, 40-bit addressing
RV64IMAFDC instruction set
5 stages pipeline
Icache/Dcache: 32KB
Branch Prediction (16KB)
MMU 128 entries
FPU single and double precision
JTAG Debug interface
AXI-M Interface: Cores and MCU uses 128-bit AXI master interface with NoC NMU to store or fetch the data from the DDR Memory.
APB-S Interface: The Encoder IP provides 32-bit APB-S interface to configure encoder parameters, start processing and get results.
jTAG JTAG Interface: JTAG interface for MCU debug. The debug ports will be accessed through PL and there will be a logic in PL which would be handling MCU debug with JTAG signals.

Clock Gating: The Decoder IP supports automatic hardware clock gating at low level (handled by RTL Synthesis) and at decoder core level. The GATED_CLOCK register allows controlling the internal clock signal generation. The IP provides a hardware-controlled gated clock in which the clock gating is based on the command start and completion events.

Interconnect
For the external programming of encoder & decoder cores, interconnect connects NSU with AXI-S interface and cores with APB interface. Interconnect takes care of the data conversion from AXI-S interface to APB interface. Interconnect also handles the asynchronous clock crossings for the APB and AXI Clocks. Interconnect also provides communication between VCU SLCR with APB interface and NSU with AXI-S interface. The clock for AXI-S interface would be of 167 MHz frequency. The clock for APB interface to encoder would be max 950 MHz and the clock for APB interface to decoder would be max 918 MHz. The clock for APB interface to VCU SLCR would be 167 MHz, same as the AXI Slave clock. VCU would be configured with 128-bit wide AXI Slave Interface. The physical data width is fixed to 128 bits, but AXI-S may have narrow transactions like 32-bit transaction or 64-bit transaction. The interconnect will translate the 128-bit data on AXI-S interface to streams of 32-bit data on APB3 interface. Interconnect provides support for narrow transfer and also 128-bit data width can be used along with the strobe.
As AXI interface supports fixed bursts but APB interface does not. And SLVERR is an expected response when the master supports Fixed, and the Slave does NOT support Fixed. Generating a Slave error is the only way Arteris produces a legitimate response to a FIXED transaction is if the Master NIU supports but the Slave NIU does not support. https://jira.xilinx.com/browse/EDT-1056613
The base address from NSU to interconnect is 0xE8000000. In case of multiple VCU Tiles, NoC Remap Registers are used in NMU to remap the address for the other VCU tiles. Here, we need to Program one to 0xE8000000 and the other to base address of other VCU Tile (for example 0xE81000000).  Also, please note that we need to give the correct destination ID of the NSU of the corresponding VCU tile while doing remap register configuration.

VCU performance monitor will allow the customer/user to assess system level behavior in a non-invasive way and without burdening the design with additional soft IP. SysMon sideband channel (SSC) is used for eFuse disable of VCU. The transfer of secure e-fuse data from the PMC to the VCU cores is done using the SSC (SysMon Side Channel), a serial ring used to connect satellite SysMon instances around the chip. It was designed exclusively for the SysMon, however because it is the only private chip-wide bus, it may be repurposed prior to fabric startup to transfer the secure e-fuse values.

VCU will instantiate an “SSC receiver” circuit to observe the traffic on the SSC during fabric configuration and capture the e-fuse data from special packet types. These are unique packets that are only generated by the root SysMon for this purpose. The SSC receiver should be an observer only on the SSC to avoid interfering with the SysMon operation.

The e-fuse value in the PMC, assigned to VCU, is hard-wired from the e-fuse block to the root SysMon and the e-fuse values can be write-protected by Xilinx during manufacturing test. The root SysMon contains a state machine, triggered by SW / firmware, that generates special SSC packets using the e-fuse data. The trigger from SW prompts the root SysMon to create 4 consecutive 32-bit packets, each having a capacity to transfer 16-bits of payload, and to launch these packets onto the PL SSC ring. Only the triggering is SW controlled, the contents of the packets are hard wired and cannot be altered. There is no connection within the root SysMon between the AXI switch, or any other interface, and the SSC interface.

The root SysMon also contains some circuitry to receive and verify the secure e-fuse packets when they arrive back around the SSC ring. This circuitry can set interrupts to flag missing or corrupted packets or other unexpected behavior, however it is not a part for the system security.

The SSC control packets used to send the secure e-fuse data are formatted as follows:

All other packet types are silently ignored
Valid packets must have
control header
broadcast address

expected 2-bit word index
E-fuse words are expected in order from most to least significant
 Out of order words clear the valid flag and raise an “efuse_error” interrupt
SSC marker corruption checks in the SSC receiver are the same as in SysMon root.
Marker corruption invalidates an SSC packet and raises the efuse_error interrupt
The secure eFuse SSC packets can be sent more than once by the root and may be received more than once by the receiver, however the outgoing valid flag is not asserted until “locked” whereupon further reception is disabled. The eFuse outputs are not considered valid and may not be used unless the valid flag is asserted

NPI Scan Controllability

PCSR are not scan controlled. These are not part of scan chain. PCSR will, however receive controlled clock, same as other NPI flops.
This means, when scan clear is enabled, PCSR will receive scan clear clock. Similarly, PCSR is clocked by scan clock during stuck at mode scan testing.
Other flops in NPI are scan controlled – for both clock and reset
This is because, NPI RTL module supports only one clock
Only requirement we should ensure is, during scan clear operation PCSR bits will not be modified in the design. The interface ready could get de-asserted, PMC should retry access.
PMC will trigger scan clear, then wait for enough time for the scan clear to be done before polling for scan done and pass. There should not be any accesses during this time.

SysMon sideband channel (SSC) is used for eFuse enable/disable of VCU. The transfer of secure e-fuse data from the PMC to the VCU cores is done using the SSC (SysMon Side Channel), a serial ring used to connect satellite SysMon instances around the chip. It was designed exclusively for the SysMon, however because it is the only private chip-wide bus, it may be repurposed prior to fabric startup to transfer the secure e-fuse values.

VCU will instantiate an “SSC receiver” circuit to observe the traffic on the SSC during fabric configuration and capture the e-fuse data from special packet types. These are unique packets that are only generated by the root SysMon for this purpose. The SSC receiver should be an observer only on the SSC to avoid interfering with the SysMon operation.

The e-fuse value in the PMC, assigned to VCU, is hard-wired from the e-fuse block to the root SysMon and the e-fuse values can be write-protected by Xilinx during manufacturing test. The root SysMon contains a state machine, triggered by SW / firmware, that generates special SSC packets using the e-fuse data. The trigger from SW prompts the root SysMon to create 4 consecutive 32-bit packets, each having a capacity to transfer 16-bits of payload, and to launch these packets onto the PL SSC ring. Only the triggering is SW controlled, the contents of the packets are hard wired and cannot be altered. There is no connection within the root SysMon between the AXI switch, or any other interface, and the SSC interface.

The root SysMon also contains some circuitry to receive and verify the secure e-fuse packets when they arrive back around the SSC ring. This circuitry can set interrupts to flag missing or corrupted packets or other unexpected behavior, however it is not a part for the system security.

Observe the SSC only while ssc_efuse_en is asserted (en_glob==1 & ghigh_b==0) . Once the fabric is configured, the enable will de-assert and the receiver will no longer respond to the SSC inputs
The receiver looks for secure e-fuse packets with broadcast address only
All other packet types are silently ignored
Valid packets must have
control header
broadcast address
secure (SEC) bit 20 set
expected 2-bit word index
E-fuse words are expected in order from most to least significant
Out of order words clear the valid flag and raise an “efuse_error” interrupt
SSC marker corruption checks in the SSC receiver are the same as in SysMon root.
Marker corruption invalidates an SSC packet and also raises the efuse_error interrupt
The secure eFuse SSC packets can be sent more than once by the root and may be received more than once by the receiver; however, the outgoing valid flag is not asserted until “locked” whereupon further reception is disabled. The eFuse outputs are not considered valid and may not be used unless the valid flag is asserted
The outgoing valid flag is asserted only if all words have been received in the expected order and the lock(out) / ssc_efuse_en is de-asserted.
Once locked out, the SSC receiver state can only be cleared through the por_pl_b from PMC.
SSC packets can be interleaved with any other type of packet from SYSMON Root. But when the control and broadcast address match, Secure has to be set and word index has to be correctly decrementing with each packet. If this is violated, an error will be generated.
Note 1: IPOR must be released to start SSC eFuse packet transfer, otherwise No eFuse Error, valid interrupts can be captured by Interrupt status register.
Note 2: SSC receiver works on PL power. When there is PL power cycle, eFuse data has to be sent again otherwise VCU will be in disabled state.
Note 3: eFuse error interrupt is mainly used by SW to understand that VCU eFuse transmission errored out (kind of debug). No specific ISR expected. SW must resend eFuse data, if error occurred.

SSC Programming Sequence

The sequence of events for successful transfer of the secure e-fuse data are:
VCCINT_SOC is powered up and the NPI is operational
VCCINT (PL) is powered up but before the fabric configuration is completed
PMC Firmware would trigger the transmission of the secure e-fuse from the root SysMon
Fabric completes configuration and starts up
On detecting ssc_efuse_en==0 the SSC receiver gates off the SSC inputs and validates the SSC e-fuse packets received (if any)
SSC receiver asserts the “valid” flag provided 4 correctly sequenced and formatted SCC control packets have been received with secure bit
The efuse_valid and efuse_error would be routed back as interrupts to PMC on NPI
The efuse_disable_ip is stored as status bit in NPI
VCU Requirement for secure eFuse data transmission

VCCINT should be powered before fabric configuration is completed
PMC firmware should trigger the transmission of secure efuse data only after the VCCINT is up
Before fabric configuration is completed, the PMC firmware should complete the transmission of secure eFuse data to VCU on SSC
During PL configuration, SSC channel should not be shared for any other purposes

Interrupt
A list of interrupts available for VCU is:
NPI Interrupt
NoC transported interrupt
PL based Interrupt
VCU replaces GT and NPI interrupts 8, 9 and 10 are available to use. Interrupts 8 and 9 are for general messages and correctable error indication. Interrupt 10 is for non-correctable or fatal error notification. NPI interrupts are used for VCU initialization. Interrupt response time is not critical.
The use of PL based interrupts is possible but as a last resort like as in Diablo VCU.User interrupts are feedthrough for NMU/NSU and they get forwarded to the NPI network. They are level sensitive and are synchronized to the NPI clock once they reach NPI. Please note that this is a 4 bit wide bus. Unused interrupt pins can be tied to 0.
There could be substantial latency in servicing these interrupts due to how the NoC interrupts are ganged together in every device.  For an immediate response from the interrupt handler, NoC transported interrupts may not be the best choice of interrupts to use.  So, PL interrupts are planned for the VCU.
Hence, VCU supports:
NPI Interrupt
PL based Interrupt
NPI Interrupt

The uncorrectable interrupt (interrupt bit 10 of NPI Interrupts) is set immediately after scan clear/memclear is triggered. This cannot be masked. The interrupt will be self-cleared in VCU after successful completion of scanclear/memclear. SW has to clear the corresponding ISR bit in PMC. In other words, VCU2 NPI interrupt 10 (GT_NCR) will be asserted as soon as mem_clear_trigger or scan_clear_trigger is set and remains high until mem_clear_done or scan_clear_done is 0. This interrupt 10 during scan clear and mem clear is not maskable.
However, if SC/MC fails, the interrupt will remain asserted and ISR will be updated to indicate the same.
All NPI Non-correctable interrupts are sent only on 1 interrupt line(vcu2_npi_interrupt [10]) to PMC.
Remaining 2 interrupt lines(vcu2_npi_interrupt [8:9]) are masked by default.
For the non-correctable interrupt line, DFX unexpected activation lines are masked by default. This decision has been taken with respect to all other blocks like psxl, psxc and mmi.
The reset for Interrupt mask registers is dependent on INITSTATE
NPI Interrupts default values are 0.
Scan clear & mem clear interrupt gets asserted only on the interrupt line when that functionality is triggered representing failure throughout operation and gets de-asserted (by hardware) once the operation is done and pass.
NPI interface control signals are scan safe. (Can't issue a WR/RD command while scan clear is in progress).
IOR register is scan safe to avoid the interrupt pin toggling.
Requirements:
Interrupt should be asserted while SC/MC is triggered and de-assert on successful SC/MC, after SC PASS. PMC sees no interrupt if SC/MC is successful.
Interrupt to be self-cleared by VCU2 if SC/MC is successful.
Interrupt outputs lines to NPI/PMC should not toggle during Scan Clear
Mask the general messages and correctable interrupts at reset.
Note:
If SC/MC passes, PMC ISR will see the interrupt and software will clear the corresponding bit in PMC. VCU ISR will not see the interrupt.
If SC/MC fails, PMC ISR and VCU ISR will see the interrupt. This interrupt can be masked using IMR registers. SW should clear VCU ISR first and then PMC ISR.

VCO Frequency and MF Divider values
DPLL output is created from the Voltage Controlled Oscillator (VCO) within the DPLL. The VCO operating frequency can be determined by using the following relationship:
fvco = frefclk x M.F/ I
fclkout = fvco / O
where M.F corresponds to the fractional feedback divide value, with M being the integer part and F the fractional modulus, and O corresponds to the value of output divide. F is ignored when PLL is in integer divide mode with fractional SDM disabled.
The proposal is to use(only) If only Integer feedback divisor value is used to PLL so thatthe jitter performance is better. The jitter performance will degrade if we use fractional divisor value is used to generate the VCO frequency.
The DPLL reference clock is 133.33 MHz.  (To be reviewed). It is the ‘DDR’ reference clock generated by PMC, then routed via HNoC as ‘hsr_ref_clk’, then routed up the GTCC as ‘cpm_ref_clock’ into the DPLL ref clock input.
Each DPLL has 2 outputs that share the same VCO frequency but different output dividers.  So, for VCU you have 2 DPLLs that can have 2 independent VCO frequencies, and 4 derived clocks. Ready Signals of AXI interfaces are clamped to 0. When the block is powered off, there will be no data communication.
Valid Signals of AXI interfaces are proposed to clamp with bit ‘0’ (represents no valid data if one block is powered down)

Ready Signals of AXI interfaces are clamped to ‘1’ as per ARM recommendation (ARM doesn’t want the interconnects to freeze if the data is sent to a powered down block)

Recommended Clamp Value for all PL-VDU power domain crossing signals is ‘1’

EDT-1069519 Updates:
Arch spec requirement is to have ability to individually reset the Encoder (ENC) and Decoder (DEC) cores (incl the RISC-V MCU contained within the cores). This was missed in the current implementation in which the VCU2 tile has only one source for HW reset (From PL) which will reset the entire VCU2 tile. As a result, failure/hang condition in either ENC or DEC cores will affect both and will require full VCU2 tile reset. The encoder and decoder functions are completely independent – normal operation of each function will be completely un-affected and un-interrupted by any operations and events within the other function. Thus, we need separate resets for encoder and decoder cores respectively.
Fix is to have two additional HW reset sources. Spare input pins from PL will be repurposed and combined with the reset to encoder and decoder blocks. Updates in RED in Figure 11.
These resets need be asserted only when the Encoder/Decoder cores experience a hang type situation or end up in an un-recoverable error states and asserting hard reset is the only way to recover. These resets can be kept in de-asserted state during initialization and in normal operations.

SEU

An introduction to SEU can be seen below referred from SEU/SEE Arch spec.
 HYPERLINK "https://xilinx.sharepoint.com/:w:/r/sites/eng/fdst/everest/arch/_layouts/15/Doc.aspx?sourcedoc=%7BA165F63D-BA1D-45B7-9188-33742CEA5733%7D&file=Everest_SEU_SEE_Arch_Specs_v2.0_040920.docx&wdLOR=cDDDF169C-9B33-475B-A01E-39977BEB9D6A&action=default&mobileredirect=true" https://xilinx.sharepoint.com/:w:/r/sites/eng/fdst/everest/arch/_layouts/15/Doc.aspx?sourcedoc=%7BA165F63D-BA1D-45B7-9188-33742CEA5733%7D&file=Everest_SEU_SEE_Arch_Specs_v2.0_040920.docx&wdLOR=cDDDF169C-9B33-475B-A01E-39977BEB9D6A&action=default&mobileredirect=true
As Xilinx progresses down the process nodes to deliver products with increasing features/capabilities, the configuration RAM (CRAM) density is significantly increasing. Xilinx has done a good job of keeping the FIT/Mbit for the CRAM flat or made it slightly better with advanced technology nodes. But with increasing densities, the Mbits of CRAM in the devices grow at the same rate, resulting in FIT rates of the device exceeding our customer’s system level FIT budget. 6T CRAMs are susceptible to Single-Event Upsets (SEUs) caused by cosmic particles in the form of Neutrons or secondary Alpha particles from the impurities in packaging material or interaction of the device with boron 10 (10B).
The best mitigation for SEU errors from Neutrons is to make the circuit components of FPGAs, particularly all the critical config. RAM (CRAM), block RAM (BRAM) and IO, GT registers as robust as possible. The logic registers are robust and have a low FIT (FIT = Failure in Time = 1 failure in billion device operating hours). SRAM in the form of BRAM is protected by ECC, but CRAM bit flips cannot be protected by an algorithm since any change in state changes the functionality of the device that could result in system malfunction. Hence the major focus from SEU mitigation point of view is on reducing FIT/Mb of CRAM by an order of magnitude.
RAMs

VDU reuses Allegro Decoder Core from 16 nm VCU. SEU of RAMs are handled by system level mitigation techniques that are summarized below. The reason for these mitigation factor arises, since VDU decoder cores have no ECC implementation inherently.
There are two types of RAMs used in VDU – control and data RAMs.
An error in data RAM can corrupt one or more decoded frames. However, H.264/H.265 video decoding support transfer of IDR/GDR frames. I-frames are also periodically transmitted. These frames are used to refresh reference frame and thus stop propagation of errors across multiple frames. This makes the error not perceivable and hence can be recovered. The time interval at which an I-frame is transmitted is dependent on application. For ex, if for every 60 frames one I-frame can be transmitted.
An error in control RAM can corrupt decoded frame, similar to error in data RAM. Additionally, an error in control RAM can sometimes stall decode channel. A watchdog timer is implemented in decoder which can trigger an interrupt upon timeout to detect IP stall. SW can reset the channel (or multiple channels) upon detecting IP lock.
FFs
NPI registers are used in VDU for scan clear, memory clean and bisr operations.  They have no role when decoder is operational.
NPI registers are implemented as triple redundant (TMR) to protect from SEU/error events. All other flops are transitory and need not have any SEU protection.

Interfaces
AXI-M4 Interfaces
A standard AXI master interfaces areis mainly used to read and write data to DDR Memory via NoC NMU. The AXI-M interface runs at 950 MHz for encoder and at 918 MHz for decoder. The clocks are same as the operating clock frequencies of encoder and decoder. The data width is 128 bits. Here, VCU acts as master and NMU acts as slave. One instance of VCU has 4 AXI-M interfaces with NMUs which are shared as:
2 Encoder Cores - AXI-M Interface
Encoder MCU - AXI-M Interface
1 Decoder Core - AXI-M Interface
Decoder MCU - AXI-M Interface

Figure  SEQ Figure \* ARABIC 11: AXI-M Interfaces

For AXI-M Interface, the signal flow would be as:
AXI-M Write Datapath is output to interfaceinterface, and it considers VCU as a master (VCU -> NMU)
AXI-M Read Datapath is input to interface (NMU -> VCU)
AXI-M Write/Read Address paths are output to interface (VCU -> NMU)
AXI-M Write Response is input to interface (NMU -> NSU)
AXI-M interface from NMU might have reg slices/pipes for timing control
SLCR generates PPROT signals to be driven on master interfaces
Note:
AXI-M interface from NSU might have reg slices/pipes for timing control (TBD)
 AXI Slave Interface is used to configure the core parameters, start processing, get status and results via interconnect. It is also used to use encoder cache as SRAM. AXI S interface is used to write SLCR registers.
APB & AXI-S Interface
The APB interface is used for the configuration of core parameters for encoder & decoder and also for register access. The data from NSU through an AXI4 Slave Interface is converted on APB3 interface and reaches to encoder, decoder and VCU_SLCR registers. NSU acts as a master unit and VCU acts as a slave unit to transfer the data through AXI-S interface.  The data on AXI interface is 128 bits wide and for APB interface, the data width is 32 bits.
The interconnect takes care of the data conversion from AXI to APB interface. The AXI Slave port would operate at a frequency of 167 MHz while the clock for APB interface is same as the clock for encoder & decoder. The minimum/maximum clock rates for the encoder are 540 and 950 MHz. And the minimum/maximum clock rates for the decoder are 470 MHz and 918 MHz.  The interconnect needs to be configured considering these frequencies.

Figure  SEQ Figure \* ARABIC 12: APB & AXI-S Interface

For AXI-S Interface, the signal flow would be as:
AXI-S Write Datapath is input to interfaceinterface, and it considers VCU as a slave (NSU -> VCU)
AXI-S Read Datapath is output to interface (VCU -> NSU)
AXI-S Write/Read Address paths are input to interface (NSU -> VCU)
AXI-S Write Response is output to interface (VCU -> NSU)

Note:
AXI-S interface from NSU might have reg slices/pipes for timing control (TBD)
SLCR also generates PPROT signals for security reasons (TBD)

Here, VCU acts as master and NMU acts as slave. One instance of VCU has 4 AXI-M interfaces with NMUs which are shared as:

Requirements for clocking
The GTCC has one DPLL per 1x tile and each DPLL has 2 outputs that share the same VCO frequency but different output dividers (each DPLL has 4 such outputs but only 2 of them are available to the MMD tile)
So, for VCU you have 2 DPLLs that can have 2 independent VCO frequencies, and 4 derived clocks. In mapping or connection of clocks we must make sure that encoder and decoder clocks aren’t mapped to outputs of same DLL from GTCC. The same DPLL cannot provide the required frequencies for both the encoder and decoder at same time.
